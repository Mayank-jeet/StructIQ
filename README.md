# StructIQ

Concrete compressive strength prediction, with SQL analytics and a simulated A/B (causal) experiment module on top.

A civil-engineering question ("how strong will this concrete mix be at a given age?") answered with a full, honestly evaluated ML pipeline: cleaning, leakage-safe splitting, baselines, tuning, error analysis, SHAP explanations and a final held-out test score.

## Status

| Phase | What | Status |
|---|---|---|
| 1 | Data + EDA, cleaning pipeline, leakage-safe split | Done |
| 2 | Modeling: baselines, XGBoost / LightGBM, Optuna, error analysis, SHAP, final test score | Done |
| 3 | SQL analytics layer (SQLite, window functions, CTEs) | Planned |
| 4 | Simulated A/B experiment: power analysis, CUPED, confidence intervals | Planned |
| 5 | FastAPI backend + dashboard, deployment | Planned |

## Headline results

Final model: **LightGBM**, tuned with Optuna, trained on the 8 raw ingredient and age features.

| Held-out test set (206 rows, 20.5%) | RMSE (MPa) | MAE (MPa) | R² |
|---|---|---|---|
| Always predict the average (floor) | 18.02 | 14.48 | -0.01 |
| Linear regression (+ `log_age`, `water_cement_ratio`) | 7.35 | 5.48 | 0.83 |
| **LightGBM (final)** | **6.53** | **4.30** | **0.87** |

- On the dev set, grouped 5-fold cross-validation gave RMSE 5.47, MAE 3.85, R² 0.88 for the same model.
- LightGBM beats the fair linear baseline, but by a modest margin: about 11% lower RMSE on test (about 22% in CV).
- **Main weakness:** the model under-predicts strong concrete (above 60 MPa). See [Limitations](#limitations).

## Phase 1 - Data and EDA

### Dataset
UCI *Concrete Compressive Strength* (Yeh, 1998): 1,030 lab mixes, 8 inputs, 1 target.

| Column | Meaning |
|---|---|
| `cement`, `slag`, `fly_ash`, `water`, `superplasticizer`, `coarse_agg`, `fine_agg` | kg per m³ of mix |
| `age_days` | age of the specimen when tested |
| `strength_mpa` | compressive strength (target) |

The original headers are long and messy, so columns are renamed **by position** (the order is fixed by the dataset), with a check that the column count matches.

### Cleaning decisions
- **25 exact duplicate rows removed** (they came from only 11 distinct repeated rows), leaving **1,005 rows**. Duplicates removed before any split so identical rows cannot land in both train and test.
- **No missing values.**
- **Zeros are real.** Cement, water and both aggregates are never 0. Slag (46.3% zeros), fly ash (53.8%) and superplasticizer (37.6%) are optional ingredients, where 0 means "not used". They are not filled or "fixed".
- Value ranges are physically sensible (e.g. water about 122-247, cement about 102-540, strength 2.3-82.6 MPa).

### EDA findings
- **Age is very uneven.** Age 28 is 419 of 1,005 rows (42%) because 28 days is the standard age at which concrete strength is specified. Ages 3 and 7 together are 251 (25%). Ages of 90 days or more are only 185 rows (18%). The observed ages are 1, 3, 7, 14, 28, 56, 90, 91, 100, 120, 180, 270, 360, 365 (90 and 91 are essentially the same test age).
- **No single feature is strongly linear with strength.**

| Feature | Pearson | Spearman |
|---|---|---|
| cement | 0.49 | 0.46 |
| superplasticizer | 0.34 | 0.32 |
| age_days | 0.34 | **0.61** |
| slag | 0.10 | 0.14 |
| fly_ash | -0.08 | -0.06 |
| coarse_agg | -0.14 | -0.16 |
| fine_agg | -0.19 | -0.19 |
| water | -0.27 | -0.28 |

- The gap between Pearson and Spearman for age (0.34 vs 0.61) shows a relationship that always rises but is **curved** (fast early gain, then flattening). A straight line cannot follow it, which explains why a linear model needs help (see Phase 2).
- Strength depends on **combinations** (cement, water, age), not on any one feature.

### Leakage-safe split (the key design decision)
The same recipe is often tested at several ages (for example a mix at 3, 7 and 28 days). Those rows are strongly related, so a plain random row split would put some ages of a recipe in train and others in test, and the model would partly recognise the recipe. Instead:

1. A **recipe** = all 7 ingredient amounts identical (age ignored). The 1,005 rows contain **428 recipes** (about 2.3 rows each).
2. **Dev / test split by recipe, not by row** (`GroupShuffleSplit`, 20% of recipes to test, seed 42): **799 dev rows, 206 test rows (20.5%)**. A check raises an error if any recipe appears in both. Mean strength is 35.0 (dev) vs 36.4 (test), close enough that the split was not re-drawn (re-drawing until the means match would be tuning the test set).
3. **Cross-validation inside dev uses `GroupKFold(5)`**, so folds also keep recipes together.
4. **Dev/test with CV, not train/val/test.** With about 800 dev rows, a fixed validation set of about 150 rows gives a noisy score, whereas 5-fold CV uses all dev data. The test set is opened once, at the end.

The cleaning and split logic lives in `src/features.py` (single source of truth for notebooks, training and the API), and it is covered by tests.

## Phase 2 - Modeling

### Evaluation protocol
- All model selection uses **dev only**, with grouped 5-fold CV (`n_splits=5` is how the model is measured, not something to tune).
- Metrics: RMSE (typical error, punishes big misses), MAE (average miss, easiest to read), R² (share of variation explained). All errors in MPa.

### Baselines (CV on dev)

| Model | RMSE | MAE | R² |
|---|---|---|---|
| Mean predictor (always the average) | 15.79 ± 0.78 | 12.80 | -0.00 |
| Linear regression, raw 8 features | 10.33 ± 0.80 | 8.23 | 0.57 |
| Linear + `log_age` | 7.08 | 5.55 | 0.80 |
| Linear + `water_cement_ratio` | 10.30 | 8.15 | 0.57 |
| Linear + both | **7.03 ± 0.42** | 5.54 | 0.80 |

- **`log_age` is the entire gain** for linear regression (R² 0.57 to 0.80), because it straightens the age curve.
- `water_cement_ratio` alone changed nothing; on top of `log_age` the change (7.08 to 7.03) is inside fold-to-fold noise. No claim of improvement.
- **The baseline to beat is the improved linear model (RMSE about 7.0), not the raw one.** Comparing trees only with the weak baseline would have exaggerated their advantage.

### Gradient-boosted trees, default settings (CV on dev)

| Model | Features | RMSE | MAE | R² |
|---|---|---|---|---|
| XGBoost | raw 8 | 5.80 ± 1.13 | 4.20 | 0.86 |
| XGBoost | + both engineered | 5.85 ± 0.94 | 4.20 | 0.86 |
| LightGBM | raw 8 | 5.70 ± 0.99 | 4.17 | 0.87 |
| LightGBM | + both engineered | 5.65 ± 0.99 | 4.13 | 0.87 |

- Both tree models beat the best linear model by about 1.3 RMSE, in every row. The two libraries are tied.
- **Feature ablation for trees** (each feature added alone, compared with raw 8 on the same folds):
  - `log_age`: no change for either model (trees split on thresholds, so a monotone transform like log leaves the splits unchanged).
  - `water_cement_ratio`: XGBoost +0.05 (better in 2 of 5 folds), LightGBM -0.05 (better in 4 of 5). Tiny, opposite in sign, far smaller than the fold spread of about 1.0.
- **Decision: the tree models use the raw 8 features.** Rule used: keep a feature only if it helps beyond noise for the model that ships. This keeps the API simple (no feature computation at prediction time). The engineered features stay only for the linear baseline.

### Hyperparameter tuning (Optuna)
- 50 trials per model, TPE sampler with a fixed seed, each trial scored by the same grouped 5-fold CV.
- A first round with narrower ranges reached CV RMSE 5.43 (XGBoost) and 5.44 (LightGBM). Because the best values sat at the edge of their ranges (`num_leaves` 62 of 64, `min_child_weight` 8 of 10), the ranges were widened **once**.
- Final round: XGBoost 5.80 to **5.52**, LightGBM 5.70 to **5.40**. XGBoost got slightly worse than round 1 with a superset of the search space, so differences of about 0.1 are search noise, not real.
- LightGBM's `num_leaves` was again near its limit, but with about 640 training rows and `min_child_samples` of 9 a tree cannot use many more leaves, so the search was drifting across a flat region. No further widening.
- **Final choice: LightGBM** (lowest CV RMSE; the margin over XGBoost is within noise).
- Tuned LightGBM: `n_estimators` 412, `learning_rate` 0.0465, `num_leaves` 116, `min_child_samples` 9, `subsample` 0.876, `colsample_bytree` 0.993, `reg_lambda` 0.218.
- Caveat: tuned CV scores are slightly optimistic, because the settings were chosen on those same folds. The test set gives the honest number.

### Error analysis (dev, out-of-fold predictions of the tuned LightGBM)
Overall: RMSE 5.47, MAE 3.85, R² 0.88. `bias` = mean of (prediction - truth); negative means under-prediction.

| True strength (MPa) | rows | MAE | RMSE | bias |
|---|---|---|---|---|
| up to 20 | 151 | 2.65 | 4.02 | +1.41 |
| 20 to 40 | 367 | 3.41 | 4.84 | +0.98 |
| 40 to 60 | 225 | 4.49 | 6.04 | -1.71 |
| **60 to 90** | **56** | **7.40** | **9.13** | **-6.21** |

| Age (days) | rows | MAE | RMSE | bias |
|---|---|---|---|---|
| 1 to 3 | 102 | 3.65 | 5.01 | +0.22 |
| 4 to 7 | 95 | 3.78 | 5.34 | +0.40 |
| 8 to 14 | 51 | 4.33 | 5.79 | -0.83 |
| 15 to 28 | 335 | 3.50 | 5.36 | -0.22 |
| 29 to 56 (only age 56) | 65 | 5.43 | 7.05 | -1.15 |
| 57 to 90 | 44 | 3.57 | 4.42 | -0.09 |
| over 90 | 107 | 4.14 | 5.48 | -0.23 |

| Cement (kg/m³) | rows | MAE | RMSE | bias |
|---|---|---|---|---|
| up to 200 | 222 | 3.21 | 4.65 | +0.04 |
| 200 to 300 | 277 | 3.70 | 5.25 | -0.25 |
| 300 to 400 | 204 | 3.88 | 5.78 | +0.01 |
| 400 to 600 | 96 | 5.69 | 6.97 | -1.04 |

- **Strong concrete is the weak spot.** Binning by the *true* strength exaggerates the effect (a selection effect), but the cement bins show the same direction, more mildly.
- Long ages (90+ days) are **not** worse than average, contrary to the initial expectation (the data is sparse there).
- The 56-day bin is the worst age bin. Its cause is **unexplained** (see SHAP below).

### SHAP explanations
SHAP splits each prediction into a baseline (the model's average output) plus one contribution per feature, in MPa. The final model was explained on dev rows (in-sample: this shows what the model learned, not how well it generalizes).

| Feature | mean abs SHAP (MPa) |
|---|---|
| age_days | 7.30 |
| cement | 5.95 |
| water | 3.82 |
| slag | 2.87 |
| superplasticizer | 2.17 |
| fine_agg | 1.46 |
| coarse_agg | 0.77 |
| fly_ash | 0.37 |

- **The model learned sensible physics:** more cement, slag, superplasticizer and age push strength up; more water and aggregate push it down. The age effect flattens at high ages.
- **Hypotheses from EDA, tested:**
  - *Fly ash depends on age:* **not supported.** Fly ash barely matters, and its mean SHAP shows no age pattern (0.15, 0.20, -0.07 for up to 7 days, 8-28 days, over 28 days).
  - *Slag depends on age:* **partly supported.** Slag contributes +1.29 at 7 days or less and +3.12 at 8-28 days, consistent with slow early hydration, but not more after 28 days (+1.98). The age groups contain different mixes, so this is suggestive only.
  - *The 56-day errors come from slag / fly-ash mixes:* **not supported.** The cause stays unexplained.
  - *Superplasticizer acts through lower water:* water and superplasticizer have correlation -0.63, so mixes with superplasticizer use less water and SHAP credit is shared between the two. They should not be read as independent effects.
- SHAP explains the **model**, not the physics. "Cement pushes the prediction up" does not prove that adding cement strengthens concrete.

### Final model and test score
Trained on all of dev with the tuned settings, scored on the held-out test set **once** (table in [Headline results](#headline-results)). Nothing about the model was changed after seeing this score.

| Test strength bin (MPa) | rows | MAE | RMSE | bias |
|---|---|---|---|---|
| up to 20 | 45 | 1.97 | 2.81 | +1.42 |
| 20 to 40 | 82 | 3.17 | 4.69 | +0.83 |
| 40 to 60 | 56 | 5.12 | 6.48 | -0.22 |
| **60 to 90** | **23** | **10.87** | **13.63** | **-9.99** |

- Test RMSE (6.53) is worse than CV (5.47). Most of the gap comes from the strong-concrete bin: the 23 rows above 60 MPa (11% of test, against 7% of dev) account for about half of the total squared error. Excluding that bin, test RMSE is about 4.96 against about 5.09 on dev (derived from the binned errors). On ordinary concrete the model generalizes as CV predicted.
- The tuned CV score was also slightly optimistic, as noted above.
- Saved to `backend/artifacts/`: `model.pkl` and `metadata.json` (feature order, tuned parameters, CV and test scores, row counts, LightGBM version).

### Attempts to fix the high-strength under-prediction
Candidates were judged on dev out-of-fold predictions only, with a rule fixed before running: adopt a variant only if overall RMSE is no worse than baseline by more than 0.1 **and** the 60+ MPa bin clearly improves.

| Variant | RMSE | 60+ MPa MAE | 60+ MPa bias | Verdict |
|---|---|---|---|---|
| Tuned baseline | 5.47 | 7.40 | -6.21 | kept |
| Monotone constraints (cement up, water down, age up) | 5.58 | 6.82 | -4.06 | not adopted (RMSE +0.11, gain within noise) |
| `linear_tree` (linear models in leaves) | 7296 | 1427 | -110 | failed (wild extrapolation) |
| Weight x3 for rows above 50 MPa | 5.57 | 7.63 | -6.37 | no help |

- Extra weight did not help, which points to **too little data above 60 MPa (about 7% of rows)**, not to the loss function.
- Monotone constraints are the most promising direction if this is revisited.
- The original tuned LightGBM stays the final model, and the test set was looked at once.

## Design decisions and lessons
- **Split by recipe, not by row**, to stop the same mix leaking across ages. Cleaning happens before splitting.
- **Compare against a fair baseline.** Giving linear regression `log_age` raised it from R² 0.57 to 0.80 and shrank the apparent advantage of tree models.
- **Decide rules before looking at results** (feature-keeping rule, adoption rule for fixes), and report non-results and unsupported hypotheses.
- **Search noise is about 0.1 RMSE**, so differences smaller than that are not claimed.
- **The test set is opened once.** Cleaning, splitting and feature logic live in tested `src/` code, with notebooks used for exploration and findings.
- Raw data is never edited; processed data is regenerated by code.

## Limitations
- **Strong concrete (above 60 MPa) is under-predicted** by roughly 6 to 10 MPa on average. Only about 7% of rows are in that range, and trees cannot extrapolate beyond the training data.
- **Recipes are matched exactly.** Near-identical recipes (for example cement 332.5 vs 332.0) count as different, so mild leakage between them is still possible.
- The dataset is small (1,005 rows after cleaning, 428 recipes), and test-set errors in narrow bins rest on few rows (23 rows above 60 MPa).
- The 56-day error and the exact roles of correlated features (water and superplasticizer) are unexplained.
- SHAP values describe the model, not causal effects.
- The planned A/B module will be a **simulation** on top of this data. It is not a real experiment, and it will be labelled that way.
